# JWord 需求文档 + v0.1 计划审查报告

**审查日期**：2026-05-11  
**审查范围**：`docs/superpowers/specs/2026-05-10-jword-design/` 全部文档 + `docs/superpowers/plans/2026-05-11-jword-v0.1-mvp/` 全部计划  
**调研方式**：全文通读 + 全网技术调研验证

---

## 一、技术选型验证结论

### 🔴 严重问题 1：Bun + Rollup 组合不稳定

**调研发现**：Bun 在 2025-2026 年仍存在大量未解决 issue，Monorepo 场景下有构建冲突，lockfile 与 npm 不兼容，存在内存泄漏报告。

**文档现状**：`01-decisions.md` D10 直接选定 Bun workspaces，`07-engineering.md` 7.2 节有"部分依赖 require.resolve 的老 Rollup 插件若遇兼容问题，回退到 node 执行"的注脚，但严重低估了实际风险。

**建议修改**：

```
D10 修订：
- 包管理：pnpm workspaces（Monorepo）
- 脚本运行：Bun（bun test / bun run）
- 构建：Node.js + Rollup（不用 Bun 跑 Rollup）

理由：pnpm 的 workspace 协议成熟稳定，lockfile 与 npm 兼容；
Bun 的 test runner 和脚本执行速度优势保留；
Rollup 构建走 Node.js 避免兼容性问题。
```

---

### 🔴 严重问题 2：mammoth.js 保真度被严重高估

**调研发现**：
- mammoth 官方 issue #9（不支持页眉页脚）至今未关闭
- 表格只保留文本，格式全丢
- 批注支持有限
- 2025年10月发现安全漏洞（CVE-2025-11849），需升级到 v1.11.0+

**文档现状**：`05-features-l5-l7.md` L6.1 写"基于 mammoth.js 做结构化提取，保真度约 70%"。实际上对企业合同/报告场景，mammoth 的保真度只有 40~50%，且**完全不支持页眉页脚**，而页眉页脚是 D5 T2 范围的核心需求。

**建议修改**：

```
L6.1 修订：
v1.0 docx 导入：直接用 jszip + DOMParser 自研 OOXML 解析
（不用 mammoth，因为 mammoth 不支持页眉页脚且保真度不足）

覆盖范围（v1.0 T1）：
- 段落文本 + 基础格式（加粗/斜体/颜色/字号）
- 简单表格（文本内容，不含复杂样式）
- 图片（inline）
- 列表（有序/无序）

不覆盖（推迟到 v1.3）：
- 页眉页脚
- 批注
- 修订记录
- 浮动对象

mammoth 可作为"快速预览"的降级方案，不作为主路径。
```

---

### 🔴 严重问题 3：pdfmake 中文字体问题

**调研发现**：pdfmake 不原生支持中文，需手动嵌入字体并转 base64，嵌入后 PDF 文件从 90KB 膨胀到 1300KB+。更好的替代方案是 `@react-pdf/renderer`（客户端）或 Puppeteer（服务端）。

**文档现状**：`05-features-l5-l7.md` L6.3 只提到"字体嵌入可能使文件变大"，没有说明中文字体的具体处理方案。`06-performance.md` 6.8 节代码分割表格写"Pdf：+200KB（pdfmake）"，但加上中文字体实际会是 5~15MB。

**建议修改**：

```
L6.3 修订：
PDF 导出方案（两档）：

方案 A（客户端，推荐）：
- 使用 @react-pdf/renderer 替代 pdfmake
- 中文字体按需加载（用户配置字体 URL，不打入 Bundle）
- Bundle 大小：+150KB（不含字体）

方案 B（服务端，高保真）：
- 集成方自行实现：Puppeteer 截图 Canvas → PDF
- 优势：100% 与编辑器视图一致（真 WYSIWYG）
- 劣势：需要服务端资源

v1.0 默认提供方案 A，方案 B 作为可选插件接口。
```

---

### 🟡 中等问题 4：Yjs 大文档性能（已验证可行，需补充快照策略）

**调研发现**：Yjs 在 100 万字符场景下内存 112MB、解析 368ms，性能可接受。但：
- Y.Map 频繁更新会导致文档膨胀，需用 `YKeyValue` 替代
- 需要定期快照策略（每 200~500 次变更一次）

**建议补充**：在 `05-features-l5-l7.md` L5.4 补充：
> 推荐快照频率：每 200~500 次变更或每 5 分钟（取先到者）。批注存储使用 `YKeyValue` 替代 `Y.Map` 以避免文档膨胀。

---

### 🟡 中等问题 5：Canvas 编辑器的无障碍性（a11y）实现方案缺失

**调研发现**：Canvas 编辑器的屏幕阅读器支持需要维护一个隐藏的 DOM 文本镜像，文档中的 ARIA 方案不完整。

**建议补充**：在 `07-engineering.md` 7.8 节补充：
> Canvas 编辑器的屏幕阅读器支持需要维护一个隐藏的 DOM 文本镜像（`aria-hidden="false"` 的 `<div>`），与 Canvas 内容保持同步。这是 Google Docs Canvas 版本的实现方式。v0.1 可先用 `aria-live` 区域通知变更，完整 DOM 镜像推迟到 v1.0。

---

### 🟢 低优先级问题 6：性能指标表述不清

**文档现状**：`06-performance.md` 6.1 写"键入响应 ≤ 16ms（1帧）"，`01-decisions.md` D9 写"INP ≤ 100ms（P95）"，两者含义不同但文档未区分。

**建议**：在 `06-performance.md` 6.1 补充说明：
> "键入响应 ≤ 16ms"指光标更新（同步热路径）；"INP ≤ 100ms"指从用户交互到下一帧绘制的完整链路 P95 延迟，两者不矛盾。

---

### 🟢 低优先级问题 7：Yjs 双向绑定防循环机制未说明

**文档现状**：`05-features-l5-l7.md` L5.1 描述了 Model ↔ Y.Doc 映射，但没有说明如何防止双向绑定的循环触发。

**建议**：补充"双向绑定防循环机制"：
> Model 变更 → 更新 Y.Doc 时，用 `ydoc.transact(() => {...}, 'model-sync')` 标记 origin；Y.Doc observe 回调中检查 `transaction.origin === 'model-sync'` 则跳过，避免循环。

## 二、v0.1 计划具体 Bug

### Bug 1：Phase 0 依赖版本未锁定（违反 D35）

**位置**：`phase-00-setup.md` Task 0.2

**问题**：`package.json` 中 ESLint 用了 `^8.57.0`（带 `^`），违反 D35"依赖固定"原则。且 `@typescript-eslint` v8 已发布并要求 ESLint v9，带 `^` 会导致自动升级后工具链崩溃。

**修改**：
```json
"eslint": "8.57.0",
"@typescript-eslint/eslint-plugin": "7.18.0",
"@typescript-eslint/parser": "7.18.0"
```

---

### Bug 2：Phase 1 throttle 测试 flaky 风险

**位置**：`phase-01-core-foundation.md` Task 1.8

**问题**：测试用真实 `setTimeout(r, 80)` 等待 trailing call，在 CI 环境（GitHub Actions Ubuntu runner）定时器精度不稳定，有概率 flaky。

**修改**：用 `bun:test` 的 fake timers 替代：
```ts
import { mock } from 'bun:test'
// beforeEach: mock.timers.enable()
// 用 mock.timers.tick(80) 替代 await setTimeout(r, 80)
// afterEach: mock.timers.restore()
```

---

### Bug 3：Phase 2 Document 测试断言必然失败

**位置**：`phase-02-model.md` Task 2.6

**问题**：
```ts
d.update((r) => r, 'ai-assistant')  // reducer 返回同一引用
// Document.update() 检测 after === before 时直接 return，不触发事件
expect(got).toBe('ai-assistant')    // got 永远是 undefined，断言失败
```

**修改**：
```ts
d.update((r) => ({ ...r }), 'ai-assistant')  // 产生新对象才触发事件
```

---

### Bug 4：缺少早期可视化验证手段

**位置**：`plans/README.md`

**问题**：Phase 6~8 开发 Canvas 渲染/输入/UI 期间没有可运行的 demo，无法可视化验证。Phase 9 才创建 demo，但那时已经是最后阶段。

**建议**：在 Phase 1 末尾增加一个最简 vanilla demo（`examples/vanilla/index.html` + `main.ts`），Phase 6 起每个阶段都能在浏览器中验证效果。

## 三、时间估算修正

**当前估算**：2人团队并行，3~4周到v0.1

**实际风险点**：
- Phase 6（Canvas 渲染）：FontMetrics + 分词缓存 + DPR + 单页 Renderer，对无 Canvas 经验团队至少 2 周
- Phase 7（IME 输入）：IME 在 Chrome/Safari/Firefox/Windows/Mac 行为差异极大，至少 1.5 周
- Phase 0（工具链）：若遇到 Bun+Rollup 兼容问题，额外 3~5 天

**建议修改**：README 改为"2人团队并行，预计5~7周到v0.1（含调试和 IME 兼容）"

## 四、文档整体评价

| 维度 | 评分 | 说明 |
|---|---|---|
| 架构设计 | ⭐⭐⭐⭐⭐ | 分层清晰，决策有据，对标产品选择合理 |
| 技术选型 | ⭐⭐⭐ | Bun+Rollup 有风险，mammoth 保真度高估，pdfmake 中文问题未解决 |

| 风险识别 | ⭐⭐⭐ | 识别了 Canvas 性能、Yjs 绑定复杂度，但漏掉了工具链和第三方库的实际限制 |

| API 设计 | ⭐⭐⭐⭐⭐ | createInserter、Plugin API、事件系统设计都很专业 |

**总结**：架构思路正确，最需要修改的是三个技术选型问题（Bun+Rollup → pnpm+Rollup、mammoth → 自研 OOXML 解析、pdfmake → @react-pdf/renderer），以及 v0.1 计划中的两个 bug（throttle 测试 flaky、Document 测试断言错误）。修复这些问题后，文档可以直接指导实现。
